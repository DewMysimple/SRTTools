# 第二部分：P0 — 可组合、可保存的处理流程（v0.4.0 核心能力）

## 3. 产品目标与交互

在现有「批量处理」页面中增加 **「处理流程」** 模式，优先做线性多步骤工作流，不做复杂的节点连线系统。

示例：

```text
导入文件或目录
   ↓
步骤 1：删除空白字幕
   ↓
步骤 2：清理多余空格
   ↓
步骤 3：查找替换（按用户参数）
   ↓
步骤 4：简繁转换（可选）
   ↓
步骤 5：整体时间偏移（可选）
   ↓
预览影响 → 确认导出
```

主目标是用户可把几项高频操作组织为**一个可重复调用的方案**，一次作用于一个或多个字幕文件。不要让用户每执行一步都手动导出再重新导入。

UI 必须提供：
- 新建流程、添加步骤、移除步骤、上移/下移步骤、启用/禁用步骤。
- 步骤参数编辑区，沿用现有 `tool-registry.ts` 和通用参数表单。
- 从现有工具参数预设导入一步的参数（快照拷贝），不绑定到以后会改变的预设 ID。
- 流程名称、描述、步骤数、支持格式说明；保存、更新、重命名、复制、删除。
- 批量页选择某个流程、选择文件/文件夹、检查适用性、预览，再执行与导出。
- 处理过程显示当前文件与当前步骤、成功/失败/跳过、错误原因、取消和失败项重试。
- 预览沿用已有左右差异高亮，额外显示每一步变化摘要；**不必**一开始渲染每一步完整字幕快照。

**首版步骤白名单**（以真实已存在的单文件、单文档操作类型为准）：
1. 删除空白字幕。
2. 清理多余空格。
3. 查找替换（普通文本，正则若已有可靠实现可启用）。
4. 简繁转换（注意原文布局保护限制）。
5. 自动换行（只有现有规则逻辑，不做语义 AI）。
6. HTML 标签清理（须提醒可能改变文本）。
7. 时间整体偏移。
8. 重新编号（如果通过统一序列化发生隐式编号变化，预览必须如实说明）。

可在代码审计后增减白名单，但必须记录理由；**不得**将多文件合并、双语合并、拆分、独立字幕对比、文本提取、创建空白模板、写入输出目录等直接塞进“逐文件线性文档变换”步骤。这些操作的输入/输出基数或数据类型不同，应该继续作为独立工具或后续专门扩展。

## 4. 流程数据结构（建议，按仓库实际类型调整）

```ts
type WorkflowStepKind =
  | 'remove-empty'
  | 'normalize-spaces'
  | 'replace-text'
  | 'convert-chinese'
  | 'wrap-lines'
  | 'strip-html'
  | 'shift-time'
  | 'renumber';

interface WorkflowStep {
  id: string;
  operation: WorkflowStepKind;
  enabled: boolean;
  params: Record<string, unknown>;
}

interface WorkflowPreset {
  schemaVersion: 1;
  id: string;
  name: string;
  description?: string;
  steps: WorkflowStep[];
  createdAt: string;
  updatedAt: string;
}
```

这些只是逻辑模型示例；**实际 operation 值必须和仓库现有工具 ID/操作注册映射建立单一事实来源**。前端操作注册、参数校验、Worker 执行和持久化都不得各自维护互不一致的手写清单。

要求：
- schema 使用版本号，Zod 严格校验。
- Step 参数按每个工具原有参数 schema 验证；不接受不认识的操作 ID。
- 单个流程建议最多 **20 个步骤**；本机建议最多 **50 个流程**；要有字节大小限制（例如 512 KiB，按实际现有 Store 能力选取并测试）。
- Step ID 稳定、同一流程内唯一；流程名称非空、有长度限制，空白折叠处理；冲突可解释。
- 流程里**不保存**源文件路径、输出绝对路径、源文件正文、授权 token、系统凭据、可执行脚本。
- 允许确实由用户主动输入的替换文本保存在参数中，但导入/导出时明确告知这些值会随 JSON 一起分享。
- 旧的 v0.2.0/v0.3.0 工具预设格式和存储键保持兼容，不得通过升级清空现有数据。
- 保存新流程失败，保留当前正在编辑的未保存内容；读取损坏数据不能导致整个应用启动失败。
- 未来 schema 版本不可识别时，**只读隔离、警告、保留原始数据**，不静默覆盖。

## 5. 流程引擎：一次解码、一次解析、逐步变换、一次导出

建立与 React 无关、可单元测试的流程执行器，例如：

```ts
interface WorkflowExecutionContext {
  signal?: AbortSignal;
  onStepProgress?: (stepIndex: number, stepId: string) => void;
}

interface WorkflowExecutionResult {
  // 真实定义要沿用项目的 SubtitleDocument、Diagnostic 与处理摘要类型
  document: unknown;
  warnings: string[];
  stepSummaries: Array<{ stepId: string; changedCount: number; warningCount: number }>;
}
```

核心约束：
- 对每份文件只完成一次输入读取和一次解码，不为每一步导出一个 SRT 再重新解析；末端为了验证输出的合法性而再次解析最终序列化结果是允许且应保留的安全校验。
- 在**内存中的统一字幕模型**上顺序执行兼容的步骤；未启用步骤跳过。
- 完整流程通过后在末端统一执行目标格式序列化、编码和字节校验。
- 对存在原文布局保护要求的简繁转换，必须定义正确的兼容策略：可仅在安全的独立阶段使用已验证的原文跨度写回路径，或在允许丢格式布局的流程中明确提示和确认；**不能悄悄将 ASS/SSA 的格式、VTT cue 设置、控制标记破坏掉**。对于无法保证安全组合的格式/步骤，预执行阶段拒绝并解释原因。
- `renumber` 的语义需与当前导出行为一致；再次导出与预览所报告编号变化保持一致。
- 失败时停止当前文件剩余步骤，其他文件按队列策略继续；默认无部分结果导出。
- 一个文件出现无效时间、不可往返编码或无法恢复的解析错误，应按现有策略拒绝输出，而不是部分写盘。
- 取消在步骤边界和适当的长循环中及时检查；取消状态下不得产生成功的误报。
- **确认前预览与实际执行要使用相同操作路径**，避免 UI 自己做一套“看似正确”的假预览。
- 如果用户在预览后修改参数/文件/步骤，立即使旧结果失效，要求重新预览或执行。
- 对于可能改变字幕条数的步骤，后续操作应处理真实新条目集合；统计按最终逻辑条目对齐，不能按数组位置误配。
- 对同样输入、同样流程和相同参数，结果应确定性一致（允许元数据时间戳不同，但输出字幕字节应一致）。

## 6. 预执行分析与操作结果

实现 `analyzeWorkflow()` 或等价机制，在用户点击执行前：
- 校验步骤数组、参数、允许格式、是否含不兼容组合。
- 汇总哪些步骤会改变文本、时间、编号、条目数或可能导致有损转换。
- 对当前选中文件队列给出适用/不适用的明确分组。
- 展示“预估将执行 N 步、影响 M 个文件”，不要在未处理前虚构精确变化条数。
- 对确实完成预览的示例文件展示实际差异与每一步执行摘要；预览必须来自真实执行引擎。

**验收样例**：两个 SRT 输入，流程“删空白 → 清理空格 → 替换错字 → 延后 500ms”。预览与最终输出一致；原文件字节不变；可以重复执行并导出 ZIP。

# 第三部分：P0 — 流程预设与工具预设导入/导出

## 7. 「我的流程」本地保存

将 `WorkflowPreset` 接入现有持久化服务：

- 使用独立、固定且有版本号的存储键，不覆盖现有工具预设键。
- 支持新建、列出、读取、修改、重命名、复制、删除；删除前确认。
- 写入使用与现有 `preset-service.ts` 同等或更严格的串行化、容量约束和异常恢复策略。
- 显示流程创建时间、更新时间、启用步骤数。
- 保存流程只保存配置，不保存实际字幕文件、临时 Worker 数据或任务结果。
- 如果流程引用的操作在后续版本被移除/重命名，提示不可用步骤并保留原配置，不能静默删除。
- 一个损坏流程不得导致其他合法流程丢失；必要时提供可审计的“查看隔离项目”入口。

## 8. 工具预设和流程预设的 JSON 导出

现有 `src/services/preset-service.ts` 已处理工具预设；**不要新建一套不兼容的工具预设服务**。增加受控的数据交换层，至少支持：

- 导出某个工具的选中预设或用户确认的全部工具预设。
- 导出选中的流程预设或用户确认的全部流程预设。
- 统一 JSON 交换文件格式，包含 `format`、`schemaVersion`、`exportedAt`、`appVersion`、`items` 和明确的 `kind` 字段。
- JSON 中只包含确实被用户明确选择导出的配置，不包含源文件、原始字幕、系统凭据、目录授权或处理历史。
- 导出前告知：“查找/替换内容、关键词等个人输入参数可能包含敏感文本，将包含在预设文件中”。
- JSON 输出采用 UTF-8、可读缩进和固定排序规则，方便版本差异比较；文件名含固定可识别类型，例如 `SRTTools-Presets.json`。
- 完成导出后可以选择打开目录，但必须遵守当前文件服务的路径授权。

示意 schema（允许按真实实现调整）：

```json
{
  "format": "srttools-presets",
  "schemaVersion": 1,
  "appVersion": "0.4.0",
  "exportedAt": "2026-11-04T00:00:00.000Z",
  "items": [
    {
      "kind": "workflow",
      "name": "中文字幕标准清理",
      "description": "删除空白、规范空格、重新编号",
      "steps": []
    }
  ]
}
```

这个例子只是外部交换格式范本，**不得以空的 `steps` 充当真实功能样例**；正式文档还需给出一个可执行且完整的示例。

## 9. JSON 导入与冲突处理

导入必须分为：**读取 → 解析与 schema 校验 → 预览影响 → 选择冲突策略 → 确认导入 → 原子或可回滚持久化**。

必须处理：
- 文件不是 JSON、UTF-8 非法、过大、schemaVersion 未知、kind 未知、字段类型不符合要求。
- 不支持的工具 ID、未知操作、缺少参数或不合法参数、重复 ID。
- 同名项：提供**跳过 / 自动改名 / 覆盖已存在同名项**；覆盖必须经过用户确认。
- 先显示将导入多少项、跳过多少项、冲突多少项、哪些项不兼容；确认前不得更改已存数据。
- 对未来版本数据采用跳过/隔离保留策略，不能以“兼容”名义把未知字段当作有效命令执行。
- 对来自文件的 ID 不盲目信任，可重新生成本地 ID；对流程中的步骤 ID 保证唯一。
- 严格执行原有本地存储条数和字节数上限；超限要明确告知，不得截断后静默完成。
- 用户取消、写入失败或应用中断时，原来预设保持完整，不能出现一半覆盖。
- 外部 JSON 为纯配置，不能承载任意代码、URL 下载、Shell 命令或文件路径自动授权。
- 输入文件导入与预设文件导入在 UI 中明确区分，不能把预设 JSON 误当字幕源文件。

**兼容性验收**：从 0.3.0 升级到 0.4.0 后，所有合法旧工具预设仍可读取、修改、应用；导入坏 JSON 时旧数据及用户设置逐字节不变；导出后重新导入，在规范化语义上等价。

# 第四部分：P0 — 文件夹批量处理与原目录结构输出

## 10. 现状与目标

v0.3.0 已支持原生“添加文件夹”（可递归、过滤格式、扫描进度、限额、取消）。**本轮不要重复开发目录扫描器。**

本轮增强的是：用户通过文件夹加入字幕文件后，能选中一个或多个步骤的流程，对所有合法文件执行，然后**可选择按原相对路径层级导出**。

示例：

```text
输入目录：
  D:\字幕项目\剧集\S01\E01.srt
  D:\字幕项目\剧集\S01\E02.srt
  D:\字幕项目\电影\Movie.srt

输出目录（示例，不覆盖源文件）：
  D:\字幕输出\剧集\S01\E01_processed.srt
  D:\字幕输出\剧集\S01\E02_processed.srt
  D:\字幕输出\电影\Movie_processed.srt
```

用户还可以选择“全部平铺输出”或“ZIP 保留子目录”，但 Windows 下必须处理大小写不敏感文件名冲突。

## 11. 文件夹输出安全规则

- 重用 Tauri 原生目录选择、当前会话授权及既有限额，不在持久化流程配置中保存永久读取授权。
- 通过源目录的**真实根目录与真实子路径**计算相对路径。不同输入根目录重名时，采用可见的根目录别名或输出分组，不能静默覆盖。
- 绝不允许 `..`、绝对路径、盘符、UNC 注入、Zip Slip 或任何路径逃逸；必须校验规范化后的目标位于用户选中的输出根下。
- Windows 的保留名、尾部空格/点、无效字符、路径过长要有明确处理或拒绝策略。
- 对符号链接、junction/reparse point 保持已有默认拒绝/跳过策略，**不得**从输出路径追随链接绕过目录边界。
- 输出目录等于源目录、包含源目录、或被源目录包含时，要显示明确风险，默认拒绝可能导致覆盖/递归回扫的场景；允许的特殊情况须有安全验证和显式确认。
- 保留源文件不变。输出目录下目标已存在时按安全命名规则避让；若用户选择覆盖，必须有清晰二次确认、原子写入和异常恢复。
- ZIP 的 entry 路径必须经过同样校验、规范化和重名处理，解压后文件结构应与 UI 预览一致。
- 输出之前展示文件树预览（可以是简洁列表），至少包括输入相对路径、输出相对路径、重名处理和文件数统计。
- 对一个文件失败应记录原因，其他合法文件继续处理；重试只处理失败项，不能重新覆盖成功项。
- 将扫描与处理阶段分别计入进度，避免用户误以为“扫描完成”即处理完成。

## 12. 目录导出兼容与验收

至少覆盖：
- 两级及五级以内的嵌套目录。
- 同名文件位于不同目录；文件名只在大小写上不同。
- 非 ASCII 文件名：简体中文、繁体中文、emoji（系统允许时）、空格。
- 导入多根目录；输出根与源根有重叠。
- ZIP 内含不安全路径片段时必须拒绝或安全规范化。
- 文件扫描中取消、导出中取消、写入失败、目标目录被锁定。
- 选择“保持目录层级”后，输出清单与实际磁盘目录以及 ZIP 内容一致。

优先复用 `src-tauri/src/commands/folder_import.rs`、`src/services/file-service.ts`、`src/services/export-service.ts` 和已有安全写入路径。不要增加无必要的全盘访问权限。

# 第五部分：P0 — 性能基准与大文件稳定性优化

## 13. 先测量，后优化

不要首先盲目将字幕处理逻辑全部重写为 Rust，不要为了追求漂亮的指标修改产品行为。**先在 v0.3.0 代码上记录基线，再为 v0.4.0 设立客观可复现的测量办法。**

增加独立性能测试/基准脚本，例如：

```json
{
  "scripts": {
    "benchmark": "node scripts/benchmark.mjs",
    "benchmark:report": "node scripts/benchmark-report.mjs"
  }
}
```

命令仅供参考。实际脚本需与项目的 TypeScript 构建和 Worker 入口兼容；可以采用 Vitest bench 或 Node 专用基准方案，选择复杂度较低的一种。

### 基准矩阵

测试集合至少包含以下维度（通过**程序生成夹具**或仓库内合规且足够小的测试字幕生成，不将用户的真实字幕提交到仓库）：

| 类别 | 规模 | 检查点 |
|---|---|---|
| 小字幕 | 100 条 | 基础解析、处理、导出延迟 |
| 常见字幕 | 1,000 条 | 单项工具、组合三步的处理延迟 |
| 大字幕 | 10,000 条 | 变换、校验、预览摘要内存占用 |
| 很大字幕 | 50,000 条或接近现有 32 MiB 限额 | 在现有限额内测量长任务时间、峰值内存与取消 |
| 批量 | 10 / 50 / 100 文件、总大小不超 128 MiB | 排队、失败隔离、总耗时、取消与重复执行 |
| 复杂文本 | 中文、繁体、emoji、长行、多行、ASS 标记、GB18030 | 编解码正确性和性能回归 |

测量并记录：
- 输入尺寸、字幕条目数、操作/流程步骤、输出尺寸。
- 环境：Windows 版本、CPU、内存、Node/Rust、提交 SHA、构建模式。
- 每组 warm-up、至少 5 次有效运行的中位数/波动区间（按可承受的运行时间合理调整）。
- 总时长与关键阶段时间（读取、解码、解析、变换、序列化、编码、写入）。
- 可以可靠测量时记录峰值内存和 Worker 生命周期；测量不到要标注，不编造。
- 长任务取消响应时间和重复运行后内存是否持续增长。

将报告写到 `docs/PERFORMANCE_v0.4.0.md`，包含基线与优化后数据、完整命令、环境、性能取舍。**不要仅用单次运行结果宣称百分比提升**。CI 上性能测试可以作为非阻塞趋势监控，避免把共享 Runner 的波动当成回归证据。

## 14. 优化目标（优先保持正确性）

原则：
1. 所有优化必须不改变已定义的字幕业务语义和输出安全策略。
2. 优先消除流程每步重复解码、解析、序列化、复制大数组等无意义工作。
3. 避免一口气把所有中间全文、所有差异快照、所有预览页保存在 React/Zustand。
4. 大量列表只渲染当前可见范围；必要时对预览列表使用虚拟滚动或分页。
5. 逐文件执行仍为默认；如引入有限并发，需证明不会突破内存、取消与文件授权的安全边界。
6. 长时间任务需要进度/取消；必要时将 CPU 密集工作留在 Worker，避免锁死主 UI。
7. 大文本处理应避免指数级复杂度、无界正则回溯、无界差异对齐和反复全量复制。
8. 现有差异预览的条目对齐上限继续生效；对超限文件提供摘要及有限预览，不允许无响应。

建议的工程目标：
- 对常用组合操作（1,000~10,000 条），相对于“每个工具分别导出再导入”的基线，应减少重复编解码工作，并提供实测证据；不承诺凭空指定的固定加速倍数。
- 单项工具回归测试不能因新流程框架普遍变慢；超过合理波动范围（例如同环境中位数劣化 20%）时必须分析和记录原因。
- 不允许将队列限制由 100 文件 / 128 MiB、单文件 32 MiB 直接无依据放大。若要提高，单独写设计与风险评估，增加输入/内存/Windows 原生验收，不应混入默认 P0 交付。
- 性能优化不得导致字幕时间舍入、编码替代、丢失格式标记、原文布局失真。

## 15. 大文件错误与资源保障

- 超过已公布限制的文件仍被拒绝，但提示信息应包含具体限额和用户可以采取的分批处理方式。
- 对超长正则、极端长单行、几万字幕条目的处理，必须保持可取消、进度可见、错误可诊断。
- Worker 异常退出、超时或内存不足时，当前文件标记失败，其它文件按安全调度继续；不得误报全部成功。
- 多次重试不得累积未清理 Worker、Blob、文件句柄或重复事件监听。
- 基准测试生成的大型临时文件应位于项目明确的临时测试目录，测试结束自动清理；不得写入 `release-output/`。
- 开发磁盘占用报告能清楚区分临时 benchmark 产物、Vite `dist/`、Rust `target/` 和**唯一最新发布目录**。

# 第七部分：测试与验收

## 19. 自动化测试矩阵（必须新增）

### 19.1 流程引擎单元测试

1. 空流程、禁用所有步骤、1 步、3 步、20 步上限。
2. 步骤顺序变化会正确影响结果；禁用某步不执行该步骤。
3. 清理空白 → 替换 → 时间偏移后，字幕条数、正文与时间正确。
4. 使用旧工具参数 schema 校验每一步；非法正则与非法时间不能绕过校验。
5. 出错后当前文件停止，不产生部分输出；其他文件继续。
6. 预览和最终执行的业务计算结果一致。
7. 重复执行同一输入与流程得到一致的输出字节。
8. 对不可兼容的 ASS/SSA/VTT 原布局步骤组合明确拒绝或要求显式同意有损变换。
9. 执行时取消、异常 Worker 终止、清理状态和失败重试。
10. 修改参数后旧预览/旧导出状态失效；不得导出过期处理结果。

### 19.2 流程存储与预设导入导出

1. 升级 0.3.0 旧 Store 后可读取全部旧工具预设。
2. 新建/更新/删除/重命名/复制流程；空名称、重复名称、上限错误。
3. App 重启后流程仍存在，应用失败恢复不吞掉用户配置。
4. JSON 导出 → 新存储导入 → 语义一致，ID 冲突处理正确。
5. 损坏 JSON、未知 schema、未知 kind/tool ID、无效参数、超过容量。
6. 同名冲突的跳过/改名/覆盖每种策略，取消导入不改现有数据。
7. 写入失败和应用中断后旧数据完整、没有半写入。
8. JSON 中不得包含字幕正文、文件授权、绝对文件路径等非预设内容。
9. 用户输入的替换文本可以随明确导出的预设传输；显示隐私提示。

### 19.3 文件夹处理和输出

1. 两级以上的嵌套目录和多输入根。
2. 重名、大小写冲突、Unicode 路径和无效文件名。
3. 目标输出在源目录范围内、源/输出重叠时的保护。
4. `..`、绝对路径、链接/junction、ZIP 路径穿越企图。
5. ZIP 解压后目录树与预览完全一致。
6. 多文件中有失败、取消、重试时，原有成功项不被意外覆盖。
7. 所有输入源文件 SHA-256 在处理前后保持一致。

### 19.4 性能与兼容性

- SRT Parser、UTF-16、GBK/GB18030、简繁、正则、字幕对比的现有测试必须继续通过。

- 性能指标与原有代码比较，不得只记录新版本一次数据。

### 21.1 成功构建与失败恢复

- 更新产物时使用候选 staging → 完整构建/校验 → ZIP 解压运行冒烟 → 安全晋升 → 旧产物清理。
- 新构建失败时旧成功产物必须继续存在，哈希不变。
- 旧输出中出现未识别文件或疑似用户修改时，阻止自动覆盖并提示核对。
- 被正在运行的程序或文件锁占用时，不得破坏正在使用的文件。
- `release:verify` 验证所有文件大小、哈希、目录与 ZIP 字节一致、build-info、源码指纹及已记录的原生测试。
- 发布目录只有上述最新文件，不保留 `v0.1.0` / `v0.2.0` / `v0.3.0` 子文件夹、旧 ZIP、旧 Setup、额外历史备份。
- 临时 benchmark 数据和 Playwright 大报告不得拷入 `release-output/`，使用项目内受控临时目录并执行安全清理。

### 21.2 正式 Windows 构建验收

- Windows 11 当前交互环境：Tauri 启动、原生导入、组合流程处理、保存预设、重启恢复、原生导出、ZIP 解压运行和 NSIS 安装/卸载测试。
- ZIP 解压后读取字幕、执行组合流程、导出真实文件并核对内容；**仅 EXE 进程启动不算完整冒烟**。
- 测试安装和卸载后用户已有设置/预设未被意外删除；当前用户 Explorer 扩展仍保持默认关闭。
- Windows 10 / 其它 DPI / 无 WebView2 环境若没有实机，则如实标 `NOT_RUN`，不得虚报兼容。
- 正式提交构建应来自**干净工作树**；`--allow-dirty` 只能用于开发验证，`dirty: true` 不可冒充可正式发布的干净构建。
