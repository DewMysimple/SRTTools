# SRTTools 下一阶段规划：可视化字幕时间轴 + 视频预览

v0.5.0 — 时间轴工作区

v0.6.0 — 视频同步预览

Windows · Tauri 2 · React

我建议正式将时间轴纳入 SRTTools 的产品路线，但保持之前确定的核心定位：

SRTTools = 极简字幕工具箱 + 独立字幕校时工作区。

不改变现有工具箱的使用方式，不重写字幕处理引擎，也不把软件发展成复杂的视频剪辑器。

现有产品的一个重要优点是：字幕数据、UI 和 Windows 原生文件访问已经分层。因此，时间轴应该作为新的工作区接入，而不是建立第二套字幕格式解析和保存机制。

### 需要调整的一条历史设计约束

README 和功能文档目前仍把“不提供视频播放器、视频时间轴”列为产品边界。这是此前合理的设计决定，但现在用户需求已经改变。

应当将其更新为：

> 支持独立的字幕时间轴和本地视频同步预览，但不开发完整视频剪辑、多轨编辑、视频转码或云端媒体服务。

这样后续 Codex 才不会受到旧需求约束，与新的开发目标冲突。

## 二、功能规划：方案 B 的完整范围

我建议把新功能分成四个模块，先做好字幕操作，再逐步加入媒体同步。

01\. 可视化时间轴

v0.5.0 核心

- 按实际时间比例绘制字幕块。
- 拖动字幕块调整整体时间。
- 拖动左、右边缘调整开始和结束时间。
- 鼠标滚轮或按钮缩放时间轴。
- 横向滚动、跳转指定时间。
- 当前播放位置指示线（Playhead）。
- 重叠字幕显示与冲突提示。
- 时间刻度、字幕区间吸附。

02\. 字幕精细编辑

v0.5.0 核心

- 点击字幕块与字幕列表双向选中。
- 修改字幕正文。
- 精确输入开始和结束时间。
- 插入、删除字幕。
- 单条或多条字幕移动。
- 键盘微调时间。
- 撤销、重做。
- 未保存修改提示和安全导出。

03\. 本地视频预览

v0.6.0 核心

- 手动选择本地视频。
- 视频播放、暂停、跳转。
- 实时字幕叠加显示。
- 播放进度和时间轴同步。
- 点击字幕跳转视频。
- 播放速度 0.5×、0.75×、1×、1.25×、1.5×。
- 视频音量与静音。
- 设置 A/B 区间循环播放。
- 视频加载失败与编码不兼容提示。

04\. 工作区与保存管理

两个版本共同完善

- 文件修改状态显示。
- 恢复到原始文件。
- 另存为新字幕。
- 保存前检查字幕错误。
- 检查视频与字幕总时长差异。
- 可选保存工作区布局、缩放比例。
- 退出或切换文件时检查未保存内容。

其中有一条需要明确：视频仅用于校时参考，最终导出的是字幕文件，不是重新编码的视频。 这一阶段不实现视频压制、字幕烧录和视频转码。

## 四、技术实现策略

### 1. 复用现有字幕模型

我实际查看了主线的 [`src/core/models.ts`](https://github.com/DewMysimple/SRTTools/blob/main/src/core/models.ts?utm_source=chatgpt.com)。

现有字幕条目定义为：

```
export interface SubtitleCue {
  id: string;
  index: number;
  startMs: number;
  endMs: number;
  text: string;
}
```

它已经足以承载基础时间轴。

不需要另建一个 `TimelineSubtitle` 来复制所有字幕字段。可以让新增的 `TimelineSession` 引用现有的 `SubtitleDocument`，只增加编辑会话状态：

```
interface TimelineSession {
  document: SubtitleDocument;

  selectedCueIds: string[];
  playheadMs: number;

  viewportStartMs: number;
  pixelsPerSecond: number;

  isDirty: boolean;
}
```

视频状态应独立管理，例如视频路径、媒体时长、播放状态和错误类型。不应把整个视频对象或播放帧写进 Zustand。

### 2. 时间轴渲染

我推荐 React + DOM/SVG 混合渲染，第一版不要直接引入大型视频编辑框架。

| 层级    | 实现                     |
| ----- | ---------------------- |
| 时间刻度  | SVG 或 Canvas           |
| 字幕块   | 绝对定位 DOM               |
| 拖动交互  | Pointer Events         |
| 横向滚动  | 原生 Scroll + 虚拟化        |
| 字幕列表  | React 虚拟列表（有性能需求时）     |
| 播放指示线 | 独立渲染层                  |
| 编辑历史  | Command / Undo-Redo 管理 |

时间轴使用统一坐标转换：

\\[ x=(t-t_0)\times s \\]

这里的 \\(t\\) 为毫秒时间，\\(t_0\\) 为可视区域起点，\\(s\\) 为每毫秒对应的像素。

所有拖动和缩放最终都转换为整数毫秒，避免不同视图使用不同时间精度。

对于字幕重叠，默认只提示并在必要时分配临时显示行，不自动移动其他字幕。

### 3. 编辑事务与撤销重做

必须保证：鼠标拖动一条字幕 200 次，并不产生 200 个撤销步骤。

建议：

- `pointerdown`：记录原始开始、结束时间。
- `pointermove`：只更新临时预览。
- `pointerup`：校验并提交一次编辑事务。
- `Escape` / `pointercancel`：取消拖动并恢复原值。
- `Ctrl+Z`：撤销上次已提交事务。
- `Ctrl+Y` 或 `Ctrl+Shift+Z`：重做。

键盘微调也可将短时间内连续的同类操作合并为一个撤销事务。

这部分应当先写测试，再接入 UI。

### 4. 视频播放技术选型

第一选择：直接使用 WebView2 内的 HTML5 `<video>`。

暂时不引入 FFmpeg、VLC、MPV 或其他媒体播放内核。

基础文件支持先以 MP4（H.264 + AAC）为主要验收格式。WebM 可以纳入兼容测试；HEVC、MKV 等不能只看扩展名就宣称支持，因为实际解码能力取决于系统和运行时。

[image](https://www.google.com/s2/favicons?domain=https://learn.microsoft.com\&sz=32)

Microsoft Learn+1



需要在视频接入前进行一个专项技术验证：

- 视频能否播放用户选择的本地文件。
- 是否支持 HTTP Range / 分段读取及快速跳转。
- 大视频是否避免整文件加载到 JS 内存。
- 本地媒体权限是否只授予当前用户选择的文件。
- 文件关闭后是否可以释放权限和媒体资源。

Tauri 的 `convertFileSrc` 可以将本地文件转换为 WebView 可加载的资源 URL，但必须同时正确配置 Asset Protocol Scope 和 CSP。

[image](https://www.google.com/s2/favicons?domain=https://v2.tauri.app\&sz=32)

Tauri+1



特别需要注意：不能为了方便播放而给整个用户目录开放 WebView 资源访问权限。 运行时媒体授权应该限制到本次明确选择的路径。如果动态单文件授权无法满足需求，再设计经过审查的受限媒体流服务，不要退回“把完整大视频读入内存生成 Blob”的方案。

### 5. 视频与字幕如何同步？

推荐让视频成为播放状态的唯一时间来源。

```
HTMLVideoElement
      │
      ▼
读取实际播放时间
      │
      ├── 更新播放指示线
      ├── 计算当前有效字幕
      ├── 更新视频字幕叠加
      └── 必要时滚动到当前字幕
```

拖动时间轴时，反向更新视频的 `currentTime`。

播放中优先考虑 `requestVideoFrameCallback()` 获取新视频帧对应的媒体时间，并在不可用时使用 `timeupdate` 或其他适当的降级方式。但这些浏览器 API 不保证严格帧级同步，因此不要把第一版宣传成精确逐帧校时器。

[image](https://www.google.com/s2/favicons?domain=https://developer.mozilla.org\&sz=32)

MDN+1



字幕正文叠加在视频容器的独立图层中，不需要修改视频文件。

### 6. 字幕格式兼容策略

我建议首版将 SRT 作为完整可编辑格式。

| 格式        | 首版时间轴处理策略               |
| --------- | ----------------------- |
| SRT       | 完整导入、编辑、校时、导出           |
| VTT       | 允许预览；只有在验证元数据保真后开放原格式编辑 |
| ASS / SSA | 先只读预览或显式转为 SRT；必须提示样式损失 |
| CSV / TXT | 不作为首版时间轴编辑目标            |

原因是现有普通格式转换会重新序列化文件，可能丢失 ASS/SSA 样式或 VTT 专有设置。不能因为新增时间轴就让原本可保留的格式信息被悄悄丢弃。

### 需要增加的专项验收

建议作为 v0.5.0 / v0.6.0 发布门槛

验收检查项

0/10

连续缩放和横向滚动不会改变实际字幕时间

&#x20;复制验收清单

## 六、建议的版本路线

我会把开发拆成两个正式版本，以及一个可选的体验增强版本。

## v0.5.0 — 时间轴基础

先开发

目标：用户可以不依赖视频，准确地完成字幕时间修改。

交付内容：时间轴渲染、拖拽、缩放、字幕列表联动、正文修改、精确时间输入、撤销重做、校验、另存为。

## v0.6.0 — 视频同步预览

完成方案 B

目标：用户可以边看视频、边调整字幕出现和消失的时间。

交付内容：本地视频加载、安全媒体访问、播放控制、字幕叠加、播放光标同步、字幕定位跳转、速度控制、A/B 循环、媒体兼容性测试。

## v0.7.0 — 校时体验增强

可选

目标：提升高频字幕校对用户的操作效率。

可以考虑音频波形、精细吸附、更多键盘快捷键、帧率辅助刻度与双语轨道。但这些功能应根据前两个版本的实际反馈决定。

## 七、开发任务的实际执行顺序

我建议下一轮 Codex 严格按以下顺序进行，不要直接把整套时间轴和视频播放一起写出来。

| Gate | 任务          | 交付标准                       |
| ---- | ----------- | -------------------------- |
| 0    | 主线基线审计      | 核对 v0.4.0、AGENTS、现有测试和版本清单 |
| 1    | 时间轴数据与编辑事务  | 纯 TypeScript 单测全部通过        |
| 2    | 时间轴渲染和拖动    | 选中、缩放、拖动、碰撞显示均正确           |
| 3    | 字幕列表与安全导出   | 完整的无视频编辑闭环                 |
| 4    | v0.5.0 质量验收 | Chromium、Windows 和原有功能回归通过 |
| 5    | 本地视频访问验证    | 权限、分段读取、跳转和编码兼容验证通过        |
| 6    | 视频预览与时间同步   | 视频播放、字幕叠加、时间轴联动            |
| 7    | v0.6.0 发布验收 | 原生测试、文档、版本、最终产物全部合格        |

其中 Gate 5 是技术风险最高的部分，应该先单独验证，不要等整个视频 UI 做完才发现 Tauri 资源协议或 WebView2 无法正常跳转大视频。

## 九、几个我建议提前确定的产品细节

| 决策      | 我的建议                    |
| ------- | ----------------------- |
| 时间轴入口   | 左侧导航新增「字幕时间轴」，不放入普通工具分类 |
| 默认字幕轨道  | 单字幕轨道，遇到重叠时用临时分层显示      |
| 时间精度    | 内部整数毫秒，帧级定位以后再增强        |
| 默认拖动    | 保持字幕时长，整体移动             |
| 默认重叠策略  | 允许但突出警告，不自动避让           |
| 默认保存    | 另存为新文件，不覆盖原件            |
| 首版可编辑格式 | SRT                     |
| 视频选择    | 用户手动选取，不自动扫描整个目录        |
| 视频文件处理  | 只读取，不改写、不转码             |
| 编辑草稿    | 先内存保存、退出提醒；恢复机制以后评估     |
| AI 校时   | 不属于方案 B 第一轮范围           |

另外有一个容易被忽略的问题：如果用户加载的字幕时长超过视频总时长，时间轴仍然应显示那些字幕，但要用明确的视觉标记指出其超出媒体范围，不能直接截断或删除。

## 十、最终开发建议

我会为这一阶段设立三个不可妥协的原则：

第一，时间轴只能是现有业务引擎的一个新界面。 它不应该拥有一套独立的 SRT Parser、独立的时间格式规则或不兼容的导出系统。

第二，所有拖动编辑必须可撤销、可验证。 不能为了动画流畅而牺牲文件数据安全。编辑会话和批量处理结果应隔离，避免相互覆盖。

第三，先实现稳定的字幕时间轴，再接入视频。 通过 v0.5.0 和 v0.6.0 两个里程碑完成你选择的方案 B，能够显著降低对既有工具箱的影响。

这样做完后，SRTTools 将同时具备两种清晰的使用方式：普通用户继续使用轻量工具箱快速处理字幕；需要精细校时的用户进入独立工作区，通过视频和字幕时间轴进行调整。

下一步最合理的工作，就是以这份规划为基础，制定一份面向当前 `main` 真实代码的 v0.5.0 + v0.6.0 Codex 执行任务书，要求严格按 Gate 实施、测试并合并主线，而不是一次性重构现有软件。
