# 第二部分：v0.2.0 增强“处理前后预览差异”

## 四、产品目标与交互行为

用户处理字幕后，应能够在**不打开独立编辑器**的情况下快速回答：

- 哪些字幕变了？
- 变化的是文字、时间还是编号？
- 有多少条字幕被新增、删除或修改？
- 是否出现无法可靠对齐的行？
- 最终导出的内容是不是我现在看到的结果？

**必须延续现有 `ResultDetails` / `CuePreview` / `PreviewPanel` 结构。** 现有左右分栏预览可以保留布局，但要把“简单数组并排”升级为“按逻辑字幕配对的差异预览”。

## 4.1 可见 UI

在成功任务的预览区，增加：

1. **差异摘要**：新增 N、删除 N、正文变更 N、时间变更 N、编号变更 N、未变化 N；“正文+时间同时变化”的统计规则必须说明，避免重复计数导致总数对不上。
2. **过滤**：`全部` / `仅变化`。可增加“正文变化 / 时间变化 / 新增 / 删除”轻量过滤，但不是强制。
3. **左右配对展示**：每一行是一个逻辑配对，左侧“处理前”、右侧“处理后”；新增或删除时另一侧显示合理占位，不用错位字幕充数。
4. **差异高亮**：文字内的插入、删除、替换采用可访问的颜色和文本标识；时间变化单独标记，不能把整段未变正文都染色。
5. **分页**：按“**配对后的差异行**”分页，每页最多 20 行，不再分别在原始和输出数组上按相同索引截取。
6. **状态说明**：无变化、没有输出字幕文档、任务失败、报告输出、输出为空等情况，都应有清晰文案。
7. **结果一致性**：切换输出文件、筛选和翻页只影响展示，不得改变业务处理结果和导出的字节。

设计保持现有极简白色工具箱风格，深色主题也必须正常显示。差异颜色至少配合图标/文字标识，例如“新增”“删除”“文字修改”“时间调整”，不能只靠红绿颜色表达。

### 建议的界面结构

```text
处理结果
┌──────────────────────────────────────────────────────────────┐
│ 已处理 1 个文件     新增 1  删除 2  文本修改 4  时间修改 3   │
│ 过滤：[全部] [仅显示变化]                         1 / 3 页  │
├───────────────────────────┬──────────────────────────────────┤
│ 处理前                    │ 处理后                           │
│ #12  00:00:10,000         │ #12  00:00:10,000                │
│ 我觉的这个方案不错。      │ 我觉得这个方案不错。             │
│       ^^^ 高亮删除        │       ^^ 高亮新增                 │
├───────────────────────────┼──────────────────────────────────┤
│ #13  00:00:14,000         │ （已删除）                        │
│ 这是一条空白字幕          │                                  │
├───────────────────────────┼──────────────────────────────────┤
│ （新增）                  │ #14  00:00:18,000                │
│                           │ 新的一条字幕                     │
└───────────────────────────┴──────────────────────────────────┘
```

界面示例只是行为说明，最终结构应按现有组件、CSS 与可用窗口宽度设计。窗口变窄时可以改上下排列，但“逻辑配对”不能丢失。

## 4.2 差异数据模型

建议把差异计算封装为一个**纯 TypeScript、可单元测试**的模块，例如：

- `src/core/diff/subtitle-diff.ts`
- `src/core/diff/text-diff.ts`
- `src/components/subtitle-diff-preview.tsx`

实际路径可以根据仓库现有 `src/core/` 规范调整。不要把复杂的 diff 算法直接写在 JSX 里。

可参考如下结构，允许为了贴合仓库现有类型进行合理调整：

```ts
export type CueChangeType =
  | 'unchanged'
  | 'text-changed'
  | 'time-changed'
  | 'index-changed'
  | 'mixed-changed'
  | 'added'
  | 'removed'
  | 'unmatched';

export interface CueDiffRow {
  key: string;
  before?: SubtitleCue;
  after?: SubtitleCue;
  kind: CueChangeType;
  textChanged: boolean;
  timeChanged: boolean;
  indexChanged: boolean;
  matchConfidence: 'exact-id' | 'anchored' | 'heuristic' | 'unmatched';
}

export interface CueDiffSummary {
  beforeCount: number;
  afterCount: number;
  unchanged: number;
  added: number;
  removed: number;
  textChanged: number;
  timeChanged: number;
  indexChanged: number;
  ambiguous: number;
}
```

统计时提供“受影响配对行总数”作为不重叠的汇总；文字/时间/编号变化可以作为并列**属性计数**，需说明同一条可能同时进入多个属性计数，避免用户误解。

## 4.3 对齐规则：这是本功能的重点

**禁止直接 `before[i]` 对应 `after[i]`。** 必须覆盖删除、插入、重新排序、多文件合并和重复文本的场景。

建议采用分层策略：

1. **优先使用稳定的 cue ID**：如果现有处理引擎确实会在处理前后保留同一条字幕的 ID，可把 ID 当作可靠匹配标识。先验证现有变换的 ID 语义，不能无条件假设。
2. **再利用可靠锚点**：例如未变化的时间+正文、稳定的相邻关系、原始相对顺序等；仅在有根据时匹配。
3. **在局部窗口里使用序列对齐**（如 Myers/LCS 的受限版本、patience diff 或等价方案），识别插入与删除。不得在整份大型字幕上无界运行 O(N×M) 算法。
4. **重复内容存在歧义时采取保守策略**：显示无法可靠匹配/未匹配，而不是擅自把两个不同字幕硬配对，产生误导性的“文本替换”。
5. **重新排序**：尽量利用稳定 ID 显示移动或重排，至少应避免单纯因位置变化就产生虚假的“大量修改”。如果无法可靠归因，明确提示“重新排序造成配对不确定”。
6. **纯编号变更**：只标记编号变化，时间和正文不应该被报告为修改。
7. **合并 / 拆分**：一个输入对应多个输出或者多个输入对应一个输出时，优先正确展示已知结果；无法建立可靠的一对一映射时显示新增/删除/未匹配及说明，不得伪造配对。多文件合并应明确选择基于哪个输入文档显示对比，或使用输出级概览，避免仅拿第一份输入与全部合并输出比较却宣称准确。

尽量保留 O(N) 或 O(N log N) 的常见路径，必要时在长文件上采用锚点+分块策略。对超大或无法可靠对齐的文档，提供安全退化：显示数量、变化概况、原有并排预览和“无法精确对齐”的说明；不得卡死 UI。

## 4.4 字符级差异高亮

- 对已确认配对且正文不同的字幕，计算字符/词组级片段：`equal`、`insert`、`delete`。
- 中文、英文、emoji、组合字符、换行要正确显示。可以评估 `Intl.Segmenter` 按 grapheme 分割，但要考虑目标 WebView 兼容性。
- 不要为了这个功能引入大型富文本编辑器。
- 差异渲染使用 React 文本节点和 `<span>`，**不使用 `dangerouslySetInnerHTML` 注入字幕内容**。
- 正文特别长时可做局部高亮或保守退化，防止算法和 DOM 失控。
- 时间变化显示修改前后完整时间，毫秒不能丢失。
- `\n` 换行应保持可见且不影响字幕正文内容本身。

## 4.5 兼容各种输出

现有工具可能输出 SRT/VTT/ASS 类字幕文档，也可能输出 TXT、CSV、JSON 检测报告。**差异视图只在存在可比较的字幕文档时启用**。

- 有 `task.document.cues` 和 `output.document.cues`：尝试逻辑配对、摘要和高亮。
- 只有文本内容或 JSON 报告：保留原来的纯文本/报告预览，不要强行把 JSON 当字幕解析。
- 一个任务包含多个输出文件：选择输出时重新计算对应差异，并重置或夹紧分页；切换输出后不能显示上一个文件的摘要。
- 处理任务失败或取消：显示现有错误/状态，不能展示旧任务的成功差异。
- 字幕内容不同步或结构损坏：不假造对齐结果，优先显示诊断。

## 4.6 状态与性能约束

- 差异计算必须是**纯函数**，不能改写 `SubtitleDocument`、cue、`ProcessedOutput.bytes` 或原始文件。
- 仅在任务结果/所选输出变化时重新计算；使用 memoization 或明确缓存策略。
- 大文件的昂贵 diff 不能阻塞界面；必要时使用独立 Worker 或可取消异步任务。
- 在切换文件、工具、参数或输出时，**所有旧差异状态必须失效**，不允许展示与当前结果不一致的数据。
- 不能修改现有文件导出逻辑、编码转换结果和安全写入策略。

## 4.7 差异预览验收用例

至少写测试覆盖：

1. 完全相同：无变化。
2. 只修改一个中文字：正确高亮和计数。
3. 只修改时间：只显示时间变化。
4. 只重新编号：仅编号变化。
5. 删除中间字幕：删除项有占位，后续字幕仍对齐。
6. 在中间插入字幕：新增项有占位，后续字幕仍对齐。
7. 连续多条相同正文：不依赖单一文本字符串粗暴对齐。
8. 改变顺序：不虚报大量文字修改。
9. 正文含 emoji / 组合字符 / 多行：显示正确、不破坏字符。
10. 字幕条数从 41 变 39：按**差异行**分页，翻页和过滤仍准确。
11. 输出是 TXT/JSON：回退到兼容预览而不崩溃。
12. 切换输出文件：摘要、页码和高亮立刻对应当前输出。
13. 输入参数更改：旧任务结果与旧 diff 被清除，不允许直接导出旧输出。
14. 至少一份较大合成字幕文件：界面不中断、不产生无界的二次方计算。

# 第三部分：v0.2.0 工具参数预设

## 五、目标与范围

为用户提供**每个工具独立的命名参数预设**。例如“字幕文本替换”可以保存“删除特定前缀”“常用翻译修正”等参数组合，下次打开该工具可一键恢复。

### 首期必须具备

- 保存当前工具的参数为命名预设。
- 按当前工具列出预设。
- 选择并应用一个预设。
- 更新已有预设的内容（显式操作并确认）。
- 重命名预设。
- 删除预设（确认后执行）。
- 恢复当前工具默认参数。
- 应用重启后仍保留预设。
- 浏览器开发预览模式和 Tauri 桌面模式都能正常存取。
- 参数校验失败时阻止应用/保存并解释原因。
- 应用预设后，当前处理结果必须被标记为失效并清除旧的可导出状态。

**不做的内容：** 云端同步、用户账户、预设在线市场、复杂流程编排、预设分享服务。导入/导出预设文件可以留到后续版本；不要为此拖慢首期核心功能。

## 5.1 用户交互设计

在现有 `ToolWorkspace` 的“设置处理参数”区域增加简洁的预设控制栏，例如：

```text
设置处理参数
┌────────────────────────────────────────────────────────────┐
│ 参数预设 [选择预设 ▾]  [保存为新预设]  [管理预设]  [重置]   │
├────────────────────────────────────────────────────────────┤
│ 查找内容：       [ 觉的                                  ] │
│ 替换为：         [ 觉得                                  ] │
│ □ 区分大小写     □ 正则表达式                              │
└────────────────────────────────────────────────────────────┘
```

建议的行为：

1. 用户调整参数后点击“保存为新预设”，输入名称、确认保存。
2. 选择已有预设时，**只填充参数字段，不自动执行处理和导出**。
3. 应用后当前参数立即显示，出现简短反馈。
4. 若用户修改了已应用预设的参数，UI 显示“已修改”而不是暗中覆盖持久化预设。
5. 用户主动点击“更新预设”时才覆盖旧预设，弹出确认说明。
6. 删除预设必须确认；如果它正在应用，删除后参数可以保留为当前未保存值，也可恢复默认，但行为需明确且稳定。
7. “重置”只将当前表单恢复成工具默认值，**不能删除所有预设**。
8. 工具没有可配置参数时，预设栏隐藏或给出合理空状态，不显示无意义的保存按钮。
9. 全局 `busy` 或任务导出期间，禁用会造成参数变化的操作，以免与当前任务并发冲突。
10. 应用设置要兼容键盘和无障碍标签，避免仅靠图标操作。

参数预设不应抢走工具的主要视觉焦点。不要新建过度复杂的“预设管理中心”全屏页面；建议使用轻量菜单、Popover 或小型 Dialog。

## 5.2 预设数据模型

可以采用如下模型，再根据当前架构调整字段命名：

```ts
export interface ToolPreset {
  id: string;                // 稳定的 UUID
  toolId: string;            // 必须对应已注册工具
  name: string;              // 同一工具内唯一名称
  parameters: Record<string, unknown>;
  schemaVersion: 1;
  createdAt: string;
  updatedAt: string;
}

export interface ToolPresetStore {
  schemaVersion: 1;
  presets: ToolPreset[];
}
```

### 数据规则

- 保存的 **仅是 `ToolDefinition.parameters` 声明的字段与值**。
- 不保存输入文件、字幕正文、文件字节、任务输出、输出路径、临时授权 token 或完整历史数据。
- 输入编码、输出目录、文件名规则等目前属于“输入与导出选项”，**第一版不纳入工具预设**，以免错误编码或旧目录授权被隐式套用。
- 对“查找/替换”等文本参数：只有在用户显式点击保存时才写入本地。保存按钮附近可提示“预设可能包含你输入的文本，且仅保存在本机”。
- 预设仅绑定工具 ID，不得把“时间偏移”的参数应用到“文本替换”。
- 同工具预设名称大小写不敏感地比较去重；新建重复名称提示使用“更新预设”或更名。
- 名称去首尾空格，推荐限制在 1–40 个可见字符；拒绝控制字符和空白名。
- 推荐限制每个工具至多 20 个、全局至多 100 个预设，超过时提供可理解的提示。具体上限可以结合现有 Store 大小再确认。
- 列表默认按最近更新降序，也可稳定保留用户选择；不可因为读取顺序变动导致选择错误。

## 5.3 参数校验与向后兼容

**关键要求：预设属于不可信本地数据，加载时必须校验。**

- 用现有 `tools` 注册表和 `validateParameters()` 校验 `toolId`、字段名、字段类型、可选值、数值范围、数值是否有限。
- 仅保留当前工具注册表声明的字段；未知字段不得传给处理引擎。
- 旧预设缺少新字段时用该工具的 `defaultParameters()` 补齐；对类型不兼容或未知工具 ID 的预设予以隔离/忽略并提示，不得直接引发 React 异常。
- 对非法的持久化结构提供恢复方案；**不能因单个坏预设把全套设置与历史记录重置**。
- 更新现有工具参数 schema 时，通过 `schemaVersion` 做兼容迁移；不要静默应用与当前工具语义不一致的旧参数。
- 对没有参数的工具不创建空预设。
- 应用预设前先一次性生成完整、经过校验的参数对象；禁止先更新 UI 一部分字段再报错，导致半应用状态。

## 5.4 持久化实现

优先复用现有 `src/services/persistence.ts` 的桌面/浏览器双模式持久化逻辑，可以添加：

- `src/services/preset-service.ts`
- `src/components/tool-presets.tsx`
- 对应的测试文件。

建议服务接口（可依现有风格调整）：

```ts
export async function listPresets(toolId: string): Promise<ToolPreset[]>;
export async function createPreset(input: { toolId: string; name: string; parameters: Record<string, unknown> }): Promise<ToolPreset>;
export async function updatePreset(id: string, changes: { name?: string; parameters?: Record<string, unknown> }): Promise<ToolPreset>;
export async function deletePreset(id: string): Promise<void>;
```

技术要求：

1. Tauri 桌面端使用项目现有固定键持久化通道；浏览器预览使用现有 fallback。
2. 如果原生 Rust IPC Store 存在固定键白名单，要仅为预设增加适当的**固定键**（如 `tool-presets-v1`），而不是改成任意 key 的无限制读写接口。
3. 不新建 SQLite，不新增账户体系，不依赖网络。
4. 串行化读改写操作，避免快速重复保存/删除产生丢失更新的竞态；可复用历史服务的写入队列策略。
5. UI 必须等持久化读取/写入完成后才显示成功，不允许乐观地声称保存成功而实际失败。
6. 持久化失败后保留表单当前参数，弹出可重试提示，不得卡住用户继续使用字幕工具。
7. 如果保存了个人输入的查找/替换字符串，这应被视为用户主动保存的预设数据；软件本身不能将其上传。
8. 预设存储应有合理体积边界，避免用户粘贴超长文本导致本地配置不可用。

## 5.5 与现有工作区状态的集成

当前 `ToolWorkspace` 中参数初始值来自 `defaultParameters(definition)`；修改参数会清除旧任务结果。这一保护必须保留并复用。

- 每次应用/更新当前表单参数时，统一走已有的 `changeParams()` 或等价封装，确保 `invalidate()` 清掉旧的任务输出、导出路径和选中结果。
- 不能通过直接 `setParams()` 绕过结果失效逻辑。
- 路由切换到新工具后，必须显示该工具默认参数或用户明确选中的该工具预设；特别注意 React 组件复用时 `useState(initializer)` 只执行一次的问题。
- **不可自动把“最近运行参数”当作永久默认值**，用户需要显式应用命名预设。
- 允许使用当前工具默认参数的所有用户保持原本流程，不强制创建预设。
- 处理或导出期间不允许应用预设；避免旧异步任务完成后覆盖新参数状态。
- 切换预设后，现有导出结果应不能在未重新处理的情况下被导出。为此添加组件/端到端测试。

## 5.6 参数预设验收用例

至少覆盖：

1. 新建预设并保存多种类型字段（text / number / select / checkbox）。
2. 页面切换、应用重启后可以读取并应用。
3. 同一工具多个预设互不覆盖。
4. 不同工具间相同预设名称允许存在，但参数绝不串用。
5. 修改表单不自动覆盖已保存预设。
6. 更新已有预设须显式执行并正确变更 `updatedAt`。
7. 重命名、删除、删除确认取消都正常。
8. 重置当前表单不删除任何预设。
9. 非法名称、重复名称、类型不匹配、数值超限、未知 select 值被拒绝。
10. 旧 schema 缺字段时按明确规则补默认值；未知工具与损坏条目不会导致页面崩溃。
11. 持久化失败时 UI 显示错误，并保留当前参数。
12. 快速连续保存、删除不发生数据丢失。
13. 应用预设后旧处理结果失效；重新执行才产生新结果。
14. 未经用户点击保存，不会把查找文本写入持久化预设。
15. 正则参数非法时阻止应用/处理并显示校验信息。
16. 在浏览器 fallback 和 Tauri 模式都能通过各自可运行的自动/手工验证。

## 七、测试策略与命令

### 7.1 必须保留的原测试

不允许删除原有回归测试。先确认基线的通过/失败状态，改动后再对比。新增测试不能只覆盖快乐路径。

建议覆盖：

- `subtitle-diff`：配对、增删、纯时间/纯编号/文字变化、重复字幕、重排、20 行分页边界。
- `text-diff`：中英文、emoji、组合字符、换行、大文本回退。
- `preset-service`：CRUD、跨工具隔离、schema 校验、损坏数据、异步写入竞态。
- 组件测试：预设管理交互、可访问性标签、条件禁用、筛选/翻页、输出文件切换。
- E2E：用户选择文件、修改参数、处理、查看高亮差异、保存/应用预设、修改参数后旧结果失效、重新处理、导出。
- 原生安全回归：文件路径授权、原文件保护、文件名冲突、批量失败与取消。

### 7.2 重点 E2E 场景

**E2E-01：文本替换 + 差异高亮**

1. 导入含 3 条字幕的 SRT。
2. 把“觉的”替换为“觉得”。
3. 处理后显示 1 条文字修改，原始时间未变。
4. 切换“仅变化”只看到受影响的字幕。
5. 导出后重新解析输出，确认与预览结果一致。

**E2E-02：删除字幕 + 逻辑对齐**

1. 导入包含中间空白条目的 SRT。
2. 执行删除空白字幕。
3. 左右两侧正确显示删除行占位，后续字幕不发生错行。
4. 下一页仍按匹配后的行分页。

**E2E-03：预设创建 + 重启持久化**

1. 打开“查找和替换”，设置参数。
2. 保存为“常用替换”。
3. 重新加载页面或重启应用。
4. 应用“常用替换”，参数完整恢复。
5. 修改参数但不更新预设，再次应用原预设仍是保存值。

**E2E-04：预设切换导致结果失效**

1. 使用参数 A 处理得到结果 A。
2. 应用参数预设 B。
3. 旧结果、旧差异、旧导出操作不应继续被当作当前结果。
4. 重新处理得到结果 B，才允许导出 B。

**E2E-05：非字幕输出安全回退**

1. 运行输出 TXT 或 JSON 报告的工具。
2. 预览保持可用，不显示伪造的 cue 匹配。
3. 结果字节与原有处理逻辑一致。

**E2E-06：错误与恢复**

1. 输入非法预设名称、非法参数或损坏持久化数据。
2. 界面不崩溃，能看到错误原因。
3. 原先有效的预设和当前参数不会被误删。
