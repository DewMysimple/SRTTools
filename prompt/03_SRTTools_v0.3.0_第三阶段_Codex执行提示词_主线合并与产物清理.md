## 2. 合并前检查及安全步骤

在 Windows PowerShell 的实际仓库根目录运行，逐条核对，不得复制文本假装执行：

```powershell
git status --short --branch
git remote -v
git branch -vv
git rev-parse HEAD
git log --oneline --decorate -15
git fetch origin --prune
git ls-remote origin refs/heads/main refs/heads/codex/v0.1.1-v0.2.0
git rev-parse origin/main
git rev-parse origin/codex/v0.1.1-v0.2.0
git log --oneline origin/main..origin/codex/v0.1.1-v0.2.0
git diff --stat origin/main...origin/codex/v0.1.1-v0.2.0
```

检查是否有未提交/未跟踪的重要用户文件。不要覆盖它们，不得盲目 `stash`、清空目录或删分支。如有冲突风险，安全隔离当前工作树（必要时采用独立 worktree，但不要复制完整项目依赖和构建缓存），先保全再操作。

### 2.1 快进合并优先

当确认当前主线是开发分支的祖先，且本地 `main` 干净、可安全更新时：

```powershell
git switch main
git pull --ff-only origin main
git merge --ff-only origin/codex/v0.1.1-v0.2.0
```

如果不是快进，不允许用 `reset` 或强推覆盖主线。审阅双方独立提交后用正常 merge commit 整合（解决冲突必须以实际代码和测试为依据），再跑完整回归。若主线分支保护要求 PR，则生成 PR、待合法流程完成后验证 `origin/main` 包含相关提交；不要宣称 PR 创建即等于合并成功。

### 2.2 合并后验证与推送

```powershell
npm ci
npm run lint
npm run typecheck
npm test
npm run build
npm run test:e2e
cargo test --locked --manifest-path src-tauri/Cargo.toml
cargo clippy --locked --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings
```

如果 Windows 环境允许，再验证 Tauri 的真实桌面行为（至少启动、文件导入、处理、导出、预设重启）。先核实既有 Store 的 Windows 加密 AppData 恢复问题没有回归。不能把 Chromium E2E 当成 Windows 原生对话框测试。

检查合并后的 `main` 含 v0.2.0 功能与 `docs/CHANGELOG.md` 记录，并推送：

```powershell
git push origin main
git fetch origin
git ls-remote origin refs/heads/main
git status --short --branch
```

确认 `origin/main` 的提交已包含开发分支的 v0.2.0 提交；至少保存合并前 `main` SHA、开发分支 SHA、合并后 `main` SHA 和推送后远程 SHA。无需删除旧开发分支，也不得用删除分支来伪装“清理旧版本”。

### 2.3 合并阻断条件

遇到无法安全解决的 Git 冲突、远程权限不足、主线保护、测试硬失败时：保留所有本地提交与工作区；详述阻塞原因和可操作的后续步骤。**不要在未合并的旧版 `main` 上开始 v0.3.0。** 如正常 PR 流程允许且环境具备权限，可用已更新的分支继续开发，但最终必须核实合并进主线才算完成交付。

# 第二部分：最新发布产物集中管理 + 自动清理（P0，必须与 v0.3.0 一起交付）

## 3. 最终目录：只保留最新一套

用户要求：**最终可运行程序和它的 ZIP 压缩包必须放在同一个发布根目录内；开发迭代后不积累各版本残留。** 不强制使用 `dist`。本项目统一使用：

```text
SRTTools/                         # 仓库根目录
├─ release-output/                 # 唯一对用户交付的本地发布目录（Git 忽略）
│  ├─ SRTTools/                    # 最新一套可解压运行文件
│  │  ├─ subtitle-tools.exe        # 实际 exe 名称以构建产物为准
│  │  └─ ...                       # 必需的资源、DLL/sidecar（若有）
│  ├─ SRTTools.zip                 # 上述 SRTTools/ 文件夹的 ZIP 镜像
│  ├─ SRTTools-Setup.exe           # 最新 Windows NSIS 安装包
│  ├─ SHA256SUMS.txt               # 本次产物哈希（可选但推荐）
│  └─ build-info.json              # 本次版本、commit、构建时间（可选但推荐）
├─ dist/                           # Vite 前端中间产物（不是最终交付目录）
├─ src-tauri/target/               # Rust/Tauri 编译中间产物（不是交付目录）
└─ ...
```

注意：`release-output/` **只包含最新已验证构建**。不要创建 `release-output/v0.1.0/`、`v0.2.0/`、`backup/`、`old/`、带时间戳的历史版本压缩包。安装包和 ZIP 采用**固定文件名**，不随版本变化而堆积。版本信息存放 `build-info.json` 和应用自身版本中。

### 3.1 不把裸 EXE 误称为完全独立绿色版

Tauri Windows 程序通常依赖系统 WebView2 Runtime。必须对解压后的 `release-output/SRTTools/` 做真实启动和导入/导出冒烟测试，明确运行条件。若存在必须随 EXE 提供的资源、DLL、额外可执行文件或配置，必须一起放入该目录并在 ZIP 中原样保留。

如果当前 Tauri 构建不支持已验证的直接解压运行，**不得将裸 EXE + ZIP 宣称“已验证便携版”**。应诊断并解决；无法解决时保留安装包作为可验证交付物，把便携目录验收状态标为 `BLOCKED`，明确告知用户。绝不能造一个看似完整、实际无法运行的 ZIP 冒充完成。

### 3.2 构建脚本与命令

新增可维护的脚本（名称建议如下；可根据当前 npm scripts 合理调整，但要提供等价命令）：

```json
{
  "scripts": {
    "release:win": "node scripts/build-release.mjs",
    "release:verify": "node scripts/verify-release.mjs",
    "clean:outputs": "node scripts/clean-outputs.mjs",
    "disk:report": "node scripts/report-disk-usage.mjs"
  }
}
```

`release:win` 应完成以下顺序：

1. 检查 Windows 平台、架构、当前 Git 分支及工作树状态；不覆盖未知的手工文件。
2. 确认 Node/npm/Rust/Tauri 的依赖和版本符合当前配置；同步版本号。
3. 运行关键质量门槛：lint、typecheck、Vitest、build，并视环境执行 Windows Rust 检查/E2E（完整发布门槛详见第八部分）。
4. 调用 Tauri 2 真实构建流程生成 NSIS installer 与可执行程序。
5. 在**项目内受控临时目录**中准备最新发布目录：复制可运行程序及实际必需的附带文件；复制 NSIS 安装包；压缩成包含顶层 `SRTTools/` 的 `SRTTools.zip`。
6. 验证程序存在且非空、ZIP 可解压、ZIP 与目录清单及各文件 hash 一致；进行可执行的桌面冒烟测试。ZIP 不得把 `SRTTools.zip` 再打进自己。
7. 只有当新构建验证通过，才**原子或可回滚地替换** `release-output/` 的旧结果。避免先删除用户唯一的可用发布版本再发现新构建失败。
8. 成功后自动清理旧版本安装包、旧 ZIP、临时 staging、中间输出和本轮无用报告；最终 `release-output` 中只剩最新一套。失败时保留上一套最后成功产物，并清理本次半成品。
9. 记录版本、commit、生成时间、Windows 架构、文件大小和 SHA-256，给出最终绝对路径。

本项目 `src-tauri/tauri.conf.json` 当前 `frontendDist` 为 `../dist`，默认 Vite build 也输出 `dist/`。**不要把最终交付文件写进 Vite `dist/`**；保留 `dist` 作为仅供 Tauri 打包的前端资源目录，`release-output` 作为对用户交付的唯一目录。若变更 Vite 输出，必须同步更新 `frontendDist` 并测试；优先不改以减少风险。

### 3.3 清理规则：既省磁盘也安全

默认自动清理**本次构建产生且已成功复制验证的中间发布文件**：

- `src-tauri/target/release/bundle/nsis/` 中属于本项目的旧版本安装包（仅在成功复制最新安装包后）。
- 本仓库中先前版本遗留的、明确可识别的版本化 ZIP / EXE 输出（仅在授权的发布输出目录或经校验的构建输出目录内）。
- 当前发布脚本的 `.staging-*` 暂存目录、失败中间 ZIP。
- 过期或由该脚本自己产生的 `test-results/` 和 `playwright-report/` 输出；先保留本轮必要验收摘要到 `docs/`，不保存大体积旧截图。
- 若 `dist/` 作为打包中间文件且打包后不再需要，可在成功后清理，下一次打包前自动生成。

**不要默认删除**：

- `src/`、`src-tauri/src/`、`docs/`、`examples/`、`wiki_memory/`、`.git/`、测试夹具、锁文件。
- 用户持久化的应用设置、预设、处理历史、用户选择的输入输出字幕。
- `node_modules/`、npm 全局/用户缓存、Rust crates 缓存、Git 历史。
- 当前被其他进程占用的 Rust debug/target 目录，或环境变量 `CARGO_TARGET_DIR` 指向项目外的共享构建目录。

对于更严格的低占用模式，提供**显式命令**如 `npm run clean:release-cache`：在用户确认或有明确安全开关的情况下，待产物验收成功后，只对确认属于本项目的 `src-tauri/target/release` 执行受控清理（等价于在本项目中 `cargo clean --release`，不能误清理其他项目的共享 target）。这会增加下次 release 的编译时间，README 要说明。一般迭代默认保留必要的编译增量缓存，但每次只保留一套**可交付的历史构建产物**。

清理脚本**必须**具备：

1. 路径 `resolve`/`realpath` 校验，验证在指定仓库及允许清理的目录下；不可跟随 symlink/junction 穿越到外部。
2. Dry-run 预览，列出删除目标和估计大小。
3. 仅按受控白名单目录与文件名清理，不用 `rm -rf .`、`git clean -fdx`、`Remove-Item -Recurse` 指向模糊通配符。
4. 构建或校验失败时保留上一套正常运行的产物。
5. 删除前确认没有仍在使用或复制中的产物，文件锁定则报告并跳过，不强制终止任意进程。
6. 如目标目录出现非脚本创建的未知文件，应跳过并报告，不要将其当旧产物删除。
7. 多次执行结果一致；重复调用不会产生新残留。

更新 `.gitignore` 忽略 `release-output/` 和必要 staging/报告文件；确保没有错误忽略源码、正式文档或测试夹具。**不要把 EXE/ZIP/大型 build cache 提交进 Git。**

# 第三部分：v0.3.0 必做功能（P0）

## 4. 功能一：简体 / 繁体字幕转换

### 4.1 目标

在“文本处理”分类增加可独立使用、支持批量处理的 **简体 / 繁体转换**工具。它应采用成熟的**词组与词义转换**库或字典规则，不能只做单字一对一替换；完全本地运行，不调用翻译 API。

### 4.2 UI 与参数

- 工具名称：“简繁转换”。
- 默认方向：**简体 → 繁体（通用）**。
- 另一个必选方向：**繁体 → 简体**。
- 如果依赖支持且质量经过测试，可提供“台湾常用繁体 / 香港常用繁体”作为独立预设；否则不开放这两个选项。
- 显示一句说明：“这是字词转换，不等同于翻译；专有名词与歧义词建议人工核对。”
- 接入上一轮已完成的“参数预设”系统；保存的是方向等工具参数，**不保存文件路径或字幕全文**。
- 处理结果接入现有差异预览，能展示被转换的字词和变化条目数。
- 支持单文件和批量文件，时间戳、条目顺序、原有多行结构不变。

### 4.3 核心实现

- 优先评估兼容 WebView2 和浏览器开发预览的成熟离线库（例如 OpenCC 生态的 JS 实现），核对许可证、包大小、API 与稳定性；不能假定某个版本的 API 一定可用。
- 将转换封装为纯业务模块，例如 `src/core/` 下的 `convertChineseText()`，由现有 Worker 流程调用。
- 不要自动更改 ASCII、emoji、数字或普通英文。
- 对字幕正文中的 ASS 覆盖控制序列、HTML 标签、占位符等进行安全处理；能保留的标记必须完整保留，不支持的特殊语法明确提示，不能破坏标签边界。
- 不改变时间信息、编号与 cue 数量；正文中用户刻意保留的换行不应被重新排版。
- 注意单纯反复往返“简→繁→简”不一定逐字还原，**不要将完全可逆作为验收要求**；正确性以可靠词典、约定地区模式和测试样例为准。

### 4.4 验收测试

- 简体到繁体、繁体到简体的典型语句和词组。
- 一句含中文、英文、数字、标点、emoji、换行和字幕格式标记的混合文本。
- 空字幕、仅英文字幕、双语字幕、多行字幕。
- 只有正文变化，开始/结束时间、条目数量和文件顺序不变。
- 同方向转换重复执行时应保持稳定（幂等或解释明确的例外）。
- 批量处理、参数预设应用、差异预览、取消与失败隔离。

**完成定义：** 能在现有工具列表中使用、预览和导出；不是只有一个按钮或简单 `.replace()` 示例。

## 5. 功能二：GBK / GB18030 严格导出

### 5.1 目标

补齐旧版“GBK / GB18030 可手动导入，但无法导出”的能力。强调**正确字节编码与无损安全提示**，不能把 UTF-8 字节仅修改扩展名或编码标签当作 GBK/GB18030。

### 5.2 必须先分析现有边界

核对：

- 现有 `encodeText()` / `decodeBytes()` 和编码类型定义。
- 工具页导出编码选项、全局默认编码、导出设置、参数预设隔离。
- Worker 内串行化、ZIP 中二进制字节、Rust `saveOutput` 的接收和写入方式。
- 现有编码诊断、无法识别时阻止导出、写入失败保留结果等安全策略。

### 5.3 编解码策略

- 增加独立、真实可用的 `GBK` 和 `GB18030` 输出选项，不得用同一编码器伪装成两种能力。
- **不要使用浏览器原生 `TextEncoder` 假装支持 GBK / GB18030；它通常只提供 UTF-8 编码。**
- 可以采用经过验证的浏览器兼容编码库，或在 Tauri/Rust 层实现严格编码。选择前必须核对实际标准映射、打包兼容性、跨浏览器预览行为和许可证。
- Rust 代码或第三方库不能在无法覆盖 GB18030 所需字符映射时声称“完整 GB18030 支持”；必要时缩小已实现范围并明确拒绝，而非静默替换。
- 默认采用**严格无损导出**：遇到不能表示的字符，明确报错并说明所在条目、字符与建议编码；不允许静默变成 `?` / `�`。
- GBK 和 GB18030 分别有独立测试。应有至少一个 **GBK 不可表示、GB18030 可表示** 的测试字符，具体字节以真实、被验证的码表或编码实现为准。
- 对用户确认的旧编码输入，继续保留现有的手动编码确认流程；不可因新增导出选项降低原有导入保护。
- 导出“预览文本”与“实际保存字节”分离，ZIP 和单文件输出必须使用同一已验证编码产物。
- 不修改默认编码：旧用户设置保持 UTF-8 或原有默认值，新字段必须具备迁移和损坏数据回退逻辑。
- 对格式转换带来的样式丢失仍照常提示；编码转换不应掩盖格式转换警告。

### 5.4 字节级验收

建立测试向量（合成文本、无版权限制），检查：

1. GBK 常用中文的**准确字节输出**及重新解码。
2. GB18030 所支持扩展字符的**准确字节输出**及重新解码。
3. GBK 无法表示字符时的明确拒绝、定位与错误提示。
4. UTF-8 / BOM / UTF-16 LE/BE 原有往返行为无回归。
5. 带 CRLF/LF 换行、多行字幕与非 ASCII 文件名的导出。
6. 单个文件、批量输出和 ZIP 内输出字节一致。
7. 同名输出、权限失败和取消导出不破坏源文件。
8. 输入编码不确定时依旧遵守导出前确认机制。

**阻断条件：** 若可用依赖无法满足严格字节测试，保持 GB18030 选项隐藏或明确标注为未实现，记录研究证据；不要为交付勾选框牺牲数据可靠性。P0 交付报告必须明确告知是否满足完整编码目标。

## 6. 功能三：文件夹批量导入

### 6.1 目标

允许 Windows 桌面用户选择文件夹，一次性把其中的字幕文件添加到**现有文件队列**。不重新开发批量任务系统。

### 6.2 交互规范

在已有“添加文件”区域旁添加 **“添加文件夹”**（仅 Tauri 桌面模式显示；浏览器模式隐藏或清晰解释不支持原生目录访问）。

选择文件夹后：

- 默认仅扫描当前文件夹；提供“包含子文件夹”复选框（默认关闭）。
- 可筛选支持的字幕格式：默认只包含现有 `SRT/VTT/ASS/SSA/TXT/CSV` 且实际能正确识别/解析的格式。
- 按可预测的文件名顺序添加，显示扫描总数、已添加、重复、格式不支持、超限和读取失败数。
- 重复文件应按原有文件队列标识策略去重；**Windows 路径大小写不敏感**，但不能仅按文件名去重，因为不同目录可能有同名文件。
- 不清除原来已选文件，不静默改变原有文件顺序。
- 提供取消扫描；取消应保留此前成功加入的文件，或明确说明本次批次回滚策略，不能出现半更新却显示“全部成功”。
- 扫描和读取阶段有进度反馈，大文件/大量文件不得卡死主窗口。

### 6.3 原生实现与权限

- 复用 Tauri 文件选择 / Rust 文件服务和现有队列，不允许 Renderer 获得任意全盘目录遍历权限。
- 仅扫描用户这次**明确选择**的目录；递归权限只在本次明确选择“包含子文件夹”后生效。
- 安全处理符号链接、junction/reparse point、循环目录与路径穿越；默认不跟随指向目录外部的链接。
- 设置扫描硬限制（建议最大递归深度 5、候选文件上限 2000；具体阈值基于现有产品限制可调整），达到限制时停止并显示摘要，不要无限扫描。
- 继续遵守当前文件队列的硬限制（旧版为单文件 32 MiB、最多 100 文件、总量 128 MiB；以实际代码为准）。不得通过文件夹导入绕过这些限制。
- 文件路径不得被不必要地写入历史或普通日志。
- 重启应用后不能依靠旧目录字符串绕过新的用户授权。
- 若后端返回文件列表，不要以此赋予任意之后的目录扫描权限；授权作用域清晰、最小化。

### 6.4 验收测试

- 空目录、单文件、多文件、嵌套目录。
- 默认不递归；用户选择后正确递归。
- 重复导入、路径大小写差异、不同目录同名文件。
- 中文、空格、emoji、长文件名。
- 超过队列数量/体积上限；无效扩展名和损坏文件。
- 无权限目录、临时不可读文件、符号链接循环与目录外跳转。
- 扫描中取消；随后正常导入另一文件夹。
- 文件夹加入队列后，原有工具处理、导出、取消和重试仍正常。
- Windows 真实对话框在可交互桌面中验收；Playwright 浏览器 E2E 不能代替它。

**完成定义：** 真实 Windows 原生目录导入可运行、错误可恢复、数量和权限边界安全；不是仅提供目录对话框但无法真正入队。

## 7. 现有「字幕对比」工具的可视化升级

现状：工具注册表中已有 `compare`，目前主要生成不包含字幕全文的 JSON 差异报告；与此同时，v0.2.0 已有 `src/core/diff/subtitle-diff.ts` 和 `src/components/subtitle-diff-preview.tsx`。**本轮仅把已有差异组件接入对比工具，让普通用户在 UI 中直接看懂比较结果。**

要求：
- 导入恰好两个字幕文件后，直接在当前工具页显示左右可视化比较、差异摘要、仅显示变化/全部、分页、时间与正文变化。
- **两份独立来源的文件不能默认信任 cue ID 相同**；复用现有 diff 算法时必须选择“跨文档模式”（例如 `trustIds: false`），避免两个文件各自的 `cue-1` 错误配对。
- 若业务上需要“按编号”“按时间容差”比较，应清晰标注模式；保留 v0.2.0 对比的原有输入参数行为，不要未经验证改变结果含义。

- 大文件超出原引擎安全预算时继续回退到摘要/独立分页，不能绕过大小限制卡死 UI。
- 保留原有 JSON 报告导出能力；报告与 UI 的摘要统计须一致，不能让呈现层改变导出字节。
- 字幕差异预览禁止编辑用户的原文件；任何“导出差异报告”都不应包含完整字幕正文，除非未来得到单独明确的产品决策。

测试：两份完全独立的 SRT（内部 ID 看似相同）、相同字幕、插入、删除、编号差异、移动字幕、跨时间容差、emoji/组合字符、5,000 条回退、JSON 报告一致、Firefox/Chromium 仅在可支持环境做，桌面主要以 WebView2 验证。

完成定义：用户无需打开 JSON 文件即可在界面中观察两个文件差异；原有“工具处理前后预览”功能完整保留。

## 8. 参数预设与批量处理联动

现状：v0.2.0 已有 `preset-service.ts`、`tool-presets.tsx` 和固定键本地存储。**不要再创建一个 `batch-presets-v1` 或新的存储框架。**

要求：
- 批量处理页支持选择可批量执行的工具和已保存的该工具预设；没有参数的工具不显示预设入口。
- 点击“应用预设”只填充**当前批量工具的参数**，不立即执行、不改文件队列、不保存字幕全文、不越权选择目录。
- 更改工具、参数、输出编码或应用预设后，正确清除旧任务结果与旧可导出状态，避免用旧结果下载。
- “保存新预设/更新预设”继续使用既有交互和数据校验；不存在的字段、无效枚举、损坏版本要可靠降级。
- 预设仅保存工具参数，不保存文件路径、用户导出目录授权、字幕全文或当前队列。
- 同一工具在独立工具页与批量处理页应用同一预设，参数和结果应一致。
- 处理过程中禁止保存/切换预设，避免竞态；失败时参数保留可重试。
- 如原批量页已复用统一 ToolWorkspace，应优先原位扩展，**不要为该功能复制整个 ToolWorkspace**。

测试：保存→重启→批量应用、不同工具同名预设、工具切换、非法预设、处理中锁定、应用后旧导出失效、同一参数单文件与批量输出一致。

## 9. Windows Explorer 右键入口（可控、默认不启用）

目标：用户在 Windows 资源管理器选中 SRT（或其他受支持字幕格式），通过右键菜单将文件传入 SRTTools；仍由用户明确发起操作。该功能**不应在安装时未经同意修改注册表**。

实现原则：
- 首先研究 Windows 10/11 真实上下文菜单行为，明确 Windows 11 可能位于“显示更多选项”。
- 优先提供设置页的显式 `启用 / 禁用资源管理器右键菜单`，默认关闭；或安装器中清晰可见的可选项，不做强制注册。
- 采用 per-user HKCU 作用域，不要求管理员权限，不注册全盘扩展；仅针对受支持字幕文件扩展名或用户明确选择的类型。
- 注册表操作必须限制在**本应用拥有的专属键**。启用记录安装路径，卸载或禁用时只清理自己的键，不能影响用户原有菜单项。
- 严格处理引号、空格、中文、emoji、`%1`/`%*` 等 Windows 文件参数；禁止字符串拼接到 PowerShell / cmd 的不受信任 Shell 命令。
- 将命令行启动参数安全转换成应用的“用户明确选择文件”导入流程；**绝不可让任意外部启动参数直接获得 Rust 文件系统通用读写权限**。检查路径、扩展名、大小、访问范围、目录与软链接风险。
- 支持应用未运行与已运行两种场景；多实例或单实例转发必须经可靠机制验证，不能丢失用户现有队列。
- 若文件已移动、删除或无读取权限，提供明确提示而非崩溃。
- 设置里给出对 Windows 11 菜单位置的简短说明。

原生验收：启用、右键导入单个/多个文件、中文/空格路径、已运行/未运行、禁用、安装路径改变、卸载、权限错误、安装版更新、Windows 10/11 可用环境。所有测试须在**隔离的测试用户或明确备份的注册表键下**执行，退出时恢复测试前状态。

阻断与降级：如无法在真实 Windows 环境中验证注册表写入与卸载行为，功能入口保持关闭或标注实验状态，不允许在正式安装版中默认启用。P1 可以独立延后，但必须在报告中注明真实状态。

**文件队列：** 文件夹扫描、取消、递归、符号链接、目录外跳转、数量/体积上限、已在队列中的文件、不同文件夹同名字幕、临时文件不可读、空文件。

**用户体验：** 工具注册表搜索、参数预设应用、预览差异、文件变更后旧结果失效、批量失败后重试、不同窗口尺寸下的布局和清晰错误提示。

**Windows 原生：** 文件夹选择器、Explorer 文件拖放、NSIS 安装/启动/卸载、右键菜单启停（若已实现）、WebView2 运行时、含中文和 emoji 的路径、权限拒绝后恢复、设置与预设重启持久化。

**发布与磁盘：** 连续成功构建、一次成功一次失败、ZIP 文件清单与 hash、固定文件名覆盖、旧产物清理、非构建文件保护、发布目录空间稳定、清理失败不会破坏上一套成功产物。

已知上一轮在 Windows 11 100% DPI 下通过较多原生交互；Windows 10、125%/150%/200% DPI、干净系统无 WebView2、超 MAX_PATH 系统对话框未全面验证。能测试的继续补测，不能测试要如实列入风险，而非直接写 PASS。
